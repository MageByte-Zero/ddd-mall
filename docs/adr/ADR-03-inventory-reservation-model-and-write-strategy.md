# ADR-03：库存预占模型的并发写策略

- 状态：Accepted
- 日期：2026-09-29
- 决策人：专栏作者
- 关联讲次：第 12 讲（首次引入），影响第 13（幂等）、14（可靠投递）、15（退款回滚库存）、21（限流）、28（混沌）讲
- 关联夹具：`fixtures/incidents/inventory-oversold.md`、`fixtures/requirements/order-creation.md` 第 4 节不变量 2

## 背景与约束

第 10、11 讲的库存只有 `total_stock` 与 `available_stock` 两个字段，`deduct` 只减可售、
总库存从不减少。这直接违反需求文档第 4 节第 2 条的守恒不变量
「已预占库存 + 可售库存 == 总库存」——实测第 11 讲实验后库里是
`total=100 / available=93`，那 7 件没有任何字段记录其去向。

第 12 讲引入第三个字段 `reserved_stock` 后，需要决定**四个写操作各自的并发策略**。
约束有三条：

1. 预占是库存系统最热的路径，大促时同一 SKU 的行会被大量请求同时盯住；
2. 释放、出库、补货的正确性依赖守恒，而守恒由领域层计算；
3. 预占与释放都可能是 Seata AT 的分支事务，分支内不能随意开启新事务。

## 候选方案

### 方案 A：所有写操作统一走聚合整体保存 + 乐观锁（DDD 教科书写法）

- 描述：读聚合 → 领域层改 → `UPDATE ... WHERE version = ?`，冲突即失败。
- 优点：正统、统一，守恒完全由领域层把关，一条路径走到底。
- 缺点：**实测否掉了**。1000 个请求各抢 1 件、并发度 64 时，成功 **17** 次、
  版本冲突 **983** 次。乐观锁假设冲突偶发，热点库存行的冲突是必然的。

### 方案 B：所有写操作统一走原子条件更新

- 描述：把业务规则全部下沉成 SQL 的 WHERE（如 `available >= n`、
  `reserved >= n`、`available + reserved = total`）。
- 优点：吞吐最高，永不丢请求。
- 缺点：守恒逻辑散落在 SQL 里，领域层退化成"预检"，聚合根形同摆设；
  而且"释放量不得超过已预占"这类判断一旦写进 WHERE，就失去了可读的业务语义。

### 方案 C：按热度分流 ✅ 采用

- 预占（热点）→ 原子条件更新；
- 释放 / 确认出库 / 补货（低频）→ 聚合整体保存 + 乐观锁。
- 依据：两条路径保护的不是同一件事——原子条件更新保护的是**超卖这条硬底线**，
  聚合整体保存保护的是**聚合整体的守恒**。

## 决策

1. 库存聚合为三字段守恒模型，守恒在领域层守护并在重组时校验；
2. 预占走原子条件更新（`UPDATE ... WHERE available_stock >= n`，相对扣减）；
3. 释放 / 出库 / 补货走聚合整体保存 + `@Version` 乐观锁；
4. 版本冲突不重试，抛 `InventoryConcurrencyException` 并由接口层翻译为 409；
5. 库存流水 `t_inventory_log` 记在聚合之外、写在同一个本地事务里。

## 决策依据（实测数据，2026-09-29）

| 实验 | 库存 | 请求 | 成功 | 冲突/被拒 | 总耗时 | 每件摊销 |
|---|---|---|---|---|---|---|
| 防超卖（原子条件更新） | 50 | 1000 | 50 | 950 | 2200 ms | — |
| 乐观锁整体保存 | 1000 | 1000 | **17** | 983 | 1254 ms | 73.8 ms |
| 原子条件更新 | 1000 | 1000 | **1000** | 0 | 11017 ms | **11.0 ms** |
| 并发释放（乐观锁） | 已预占 100 | 100 | **2** | 98 | 314 ms | — |

乐观锁总耗时更短是假象：983 个请求什么都没做就被打发了。按成功请求摊销，
原子条件更新快 6.7 倍且不丢请求。

## 不重试的三条理由

1. MySQL 默认可重复读下，同一事务内第二次读拿到的是同一个快照，版本号不会变，
   重试多少次结果都一样；
2. 要重试必须开新事务（`REQUIRES_NEW`），这会把操作从当前 AT 分支里摘出去，
   破坏"订单和库存同成同败"；
3. 版本冲突与业务不允许是两类失败，必须分开表达（409 vs 422），
   否则调用方只能无脑重试，把"库存不足"也重试一万次。

## 后果与后续

- **收益**：守恒成立、不超卖、预占可见（为超时回收铺路）、账可追溯。
- **代价**：两条写路径并存，需要在用例编排层显式说明归属（已写在
  `InventoryRepository` 与 `InventoryApplicationService` 的 Javadoc 里）。
- **待办**：
  - 第 13 讲：引入幂等键（业务单号进请求体与流水表），端点路径一并正名为
    `/api/inventories/reservations`；
  - 第 14 讲：超时未支付预占的自动回收（依赖幂等与本讲的 `release` 能力）；
  - 第 25 讲：把"支付成功 / 发货"经事件总线接到 `confirm`。
- **回退**：预占路径从原子条件更新切回乐观锁只需改 `InventoryApplicationService.reserve`
  里的一行调用，领域层零改动。三字段退回两字段属破坏性回退，但流水表有完整前后快照，
  数据不会丢。
