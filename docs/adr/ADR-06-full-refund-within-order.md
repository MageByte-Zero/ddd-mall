# ADR-06：整单退款先放在订单聚合内

日期：2026-10-21。状态：Accepted（教学政策已获作者确认；具体实现证据见第15讲记录）。

## 背景与决策

首轮只有一笔有效整单申请，资格取决于订单状态，金额取决于实付，申请与发货互斥。Order聚合管理一个Refund实体，共用订单仓储、版本和本地事务。保留稳定申请号、金额、原因、申请前状态与最近一次结果；RefundResult不可变，成功结果要求凭证且不得降级。已有退款两条状态边补领域动作与事实，不增加独立退款服务。

申请与结果登记是两次本地事务。应用服务不判断可退资格、不直接触发渠道或库存。渠道模拟只在测试代码中提供结果，结果可信性和完整支付模型留第17讲；长流程持久化恢复留第24讲。退款事件是订单侧事实，不命令库存恢复可售，不承诺资金/库存同成同败。

## 备选

- 应用服务直接改状态：入口容易复制规则，不能保证重组和其他入口继续守住约束，未采用。
- 独立退款聚合：多笔申请、审核/撤销、部分退款、独立并发需求出现时再评估；当前拆开会额外协调申请与发货互斥，未采用。
- 独立退款服务：部署收益和团队责任无输入，不由新表或新类自动推导。

## 验证与可逆性

真实测试检查领域边界、MySQL重读、事件同事务写入、Outbox类型识别，以及同一订单版本竞争仅一方提交。测试模拟不证明渠道幂等、真实到账、AT退款或自动库存恢复。

V2扩展订单表六个可空字段及refund_no唯一键；不修改V1或旧lesson标签。旧未退款订单可重读；旧退款状态若没有身份则拒绝猜测，须人工对账迁移。以后拆出退款模型应保留refundNo及已成功事实，显式迁移额度与协作责任，不能把回滚代码当作撤销资金事实。
