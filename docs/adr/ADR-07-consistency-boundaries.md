# ADR-07 从业务完成条件选择一致性边界

2026-11-18。第 16 讲决策记录，已随正文确认。现有实现基线为 `lesson-15`。

## 决策和条件

在当前教学承诺下沿用三种边界。

1. 订单规则由聚合表达。同一订单版本的发货与退款申请由订单库的版本检查和本地事务保护。订单状态、历史和待发送事实随该事务提交。库存动作由库存负责，容量检查、预占生命周期、回执和库存写入在本地完成。
2. 创建与未支付取消继续通过 Seata AT 协调订单和库存。创建成功须有订单与预占，取消成功须有取消状态与已释放预占。该选择依赖事务标识传播、两侧代理数据源和锁检查。一阶段可见的回执或待发送行需要继续检查全局状态。恢复按协调状态和实际业务记录核对。
3. 发货成功表示订单已登记发货并持久保留事实，库存稍后按原预占确认。库存保留预占期间，这些数量已排除在可售余额之外。订单负责发送恢复，库存负责处理、重复保护和死信处置。退款申请与结果登记分别为订单本地事务，当前按模拟结果记账。未知的外部结果需要支付边界或人工对账后确认，已发货事实继续保留。

## 备选与适用性

| 备选 | 何时适用 | 当前选择的依据 |
|---|---|---|
| 单一本地事务 | 所需修改可以由同一库内事务负责 | 用于各自本地规则。两个库的独立事务加同步调用仍有分开提交的窗口 |
| 先受理再异步确认 | 业务接受可查询的待确认状态 | 需设计稳定请求身份、未确认查询、超时/重试与库存不足的结束条件。单纯替换调用机制会改变原响应含义 |
| 让发货等库存确认出库 | 发货成功必须包含仓库确认，且可以接受即时依赖 | 当前允许出库延迟并有原预占保护。引入同步依赖仍要明确跨库失败和恢复 |
| 记录进度并按条件补偿 | 已独立提交的业务步骤需要后续动作或恢复 | 退款渠道动作完成后只能按其业务能力确认或采取合法补偿。第 24 讲实现过程管理 |

## 代码与证据

`OrderApplicationService` 的创建、取消和发货入口，以及 `RefundApplicationService` 的两个入口，对应上述事务选择。`OrderRepositoryImpl` 保存订单状态、版本、历史和待发送事件。`IdempotentInventoryService`、`OutboxEventDelivery`、`ShipmentApplicationService` 分别体现库存本地保护、事务未决时的发送检查，以及库存消费的事务边界。

已有验证包括相同库存动作重放、全局未决下回执阻塞、Outbox 提交/回滚对照、消费重投、退款结果持久化和订单版本竞争。教学输入与预期见 [一致性场景](../../fixtures/requirements/consistency-scenarios.md)。真实支付回调、资金动作恢复、生产等待时限和其他并发路径仍需相应证据。

## 变更与退出条件

若产品允许先受理，定义待确认及失败等状态、创建入口身份与可查询结果后，再切换协作机制。迁移时先核清在途事务和旧预占归属，保护已持久化的动作回执与事件身份。若发货成功增加库存完成条件，重审目前的响应语义和失败处置。资金已经退回、货已发出等已确认事实继续保留，按各自政策向前处理。
