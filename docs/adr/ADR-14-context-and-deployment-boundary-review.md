# ADR-14 复审四个限界上下文与部署边界

- 状态：已采纳，适用于专栏教学工程
- 日期：2026-11-27
- 依据：`lesson-22`（`450d3784a34bc6e909994227467163e667c5c7f1`）、ADR-01、ADR-08、ADR-10 至 ADR-13
- 关联：第 23 讲复审边界，第 24 讲实现跨服务退款流程

## 决策

保留订单、商品、支付、库存四个限界上下文。课程继续采用四个现有进程。订单是按行退款额度的唯一写入方，支付负责解释渠道资金事实，库存负责预占、出库与可售，商品负责当前目录。部分退款保留在订单模型内。第 24 讲设计退款过程进度及资金结果的交接，沿用原申请身份，结果回记仍由订单执行。

四进程是当前可运行的基线。本次比较假定支付渠道适配需要独立发布，接受相应的消息恢复与运维开销。支付独立发布及售后独立团队均是教学条件，项目没有提供真实团队、容量或运营成本数据。四个 schema 表示数据所有权，基线可在同一个 MySQL 实例上承载各 schema。

## 用订单验证模型归属

已发货订单包含同一 SKU 的两条成交行。PR-A 买一根，PR-B 买两根，成交单价 ¥50，订单已接受实付 ¥150。PR-B 的原申请退一根 ¥50，结果未知。此时新申请退 PR-B 的两根，金额合计恰好 ¥150，但行用量为 3/2，拒绝登记。申请退 PR-A 的一根则符合两个上限。原申请确定成功后由在途转为已退，合计用量不变。可信的最终拒绝释放原占用，保留记录。退款不触发库存动作。

`RefundApplicationService` 在新事务加载当前 `Order` 并执行 `requestPartialRefund` 或 `recordPartialRefundResult`。`OrderRepositoryImpl` 用根版本检查竞争，再写同一事务内的退款记录。冲突后重新读取并判断，最多三次尝试。列表用 `JdbcOrderListReader` 读取已保存的退款摘要，拥有独立读事务。摘要适合展示总量，申请仍须在订单事务内按行审核。

## 以代码修订上下文关系

| 交接 | 事实与接口所有者 | 当前实现与失败责任 |
|---|---|---|
| 订单创建时读取目录 | 商品发布可购目录，订单拥有成交快照 | `CatalogOrderService` 经 `CatalogLookup` 同步取目录，下单后按成交名和单价重读。目录业务拒绝与不可用分别返回，下单不在查询失败时猜测价格。见 `order-to-catalog.yaml`。 |
| 支付确认后交给订单 | 支付发布 `PaymentSucceeded`，订单拥有受理结果及 `OrderPaid` | `SimulatedV2Protocol` 翻译外部观察，`PaymentCallbackService` 记收款及事务发件箱。`PaymentSucceededConsumer` 调用 `AcceptPaymentService`，以自己的订单状态、金额、回执及全局锁约束判断能否接受。资金已确认与订单待交接或待核查可以共存。支付侧追踪待送事实，订单侧保留自己的受理结果。见 `payment-events.yaml`。 |
| 订单预占、取消及发货 | 库存拥有预占和出库，订单拥有履约状态及 `OrderShipped` | 下单、取消走原有预占/释放 API 和 AT 路径。订单发货后经发件箱发布 `OrderShipped`，`InventoryShipmentConsumer` 按事件版本及原预占引用交给 `ShipmentApplicationService`。库存独立提交动作、流水及消费回执，消费失败按既有恢复路径处理。见 `order-to-inventory.yaml`、`order-events.yaml`。 |
| 列表读取库存观察 | 库存负责预占事实，订单负责把一次观察配回成交行 | `OrderListQueryService` 在订单只读事务结束后，经 `FeignOrderListInventory` 批量读库存。库存不可用时保留订单结果，下一次刷新按原预占号重读。现有适配器已翻译观察结果和缺失语义。若库存术语或协议开始承载不同含义，再扩大翻译范围。见 `order-list.yaml`。 |

这张关系表按实际接口与事实更新 ADR-01 的初始设想。第 19 讲实现的防腐层位于支付和模拟渠道之间。当前收款查单不提供退款结果。部分退款结果在本地 Java 用例通过受控输入回记，暂未形成支付侧退款 API 或公开事件。上下游关系可从事实和契约追溯，团队间是否有独立的供需治理另行确认。

## 候选、适用条件与触发点

| 候选 | 用同一订单检验 | 选择条件与代价 |
|---|---|---|
| 保留四上下文、四进程（采用） | 订单本地审批额度，支付提交与订单受理分开，库存仍能在订单发货后独立确认 | 复用现有运行链路，满足支付单独发布的教学条件。网络超时、交接积压、重投恢复及独立进程运维继续存在。共享的数据库实例或消息代理仍可能带来共同故障。 |
| 保留四上下文、同一进程按模块组织（备选） | 模块接口传递申请和结果，只有订单模块写退款额度。先保留分别提交的边界，订单仍可待受理，库存仍独立确认。 | 共同发版和重启可接受，且运行证据显示部署和跨进程成本足以抵偿迁移时，再评估共部署。可先用订单和支付试点，其他模块逐步复审。共同部署扩大进程故障影响，当前的同步依赖和共享事务风险需显式检查。 |
| 新增独立售后上下文（条件性候选） | 售后工单拥有审批与协作进度，获批后请求订单原子占额。支付侧确认资金结果，订单按原申请回记。相同的 3/2 拒绝仍成立。 | 独立团队持续处理多级审批、跨订单或跨渠道工单，形成独立身份、状态和规则时再建模。当前按行退款引入工单会额外协调两份进度。售后成为独立上下文后，部署仍需根据发布、故障与团队条件另作决定。 |

只放宽共同发布约束，共部署就成为可行候选。若同一进程容量仍需统一伸缩，或扩大重启影响无法接受，继续独立部署。若发布要求放宽且持续记录到序列化、配置、重投或运行维护的实际成本，共部署可以优先安排隔离验证。所有候选继续保留资金确认与订单接受两项事实，例如支付确认后，订单已取消时可记录待核查而不进入已付款。

## 验证与退出

- 已有 MySQL 证据（第 21 讲）：两个事务同读旧版本，各申请两根时只登记一笔。各申请一根时，冲突方重读可做第二笔。原申请未知保持占用，可信拒绝后可登记新号。第 22 讲独立验证两行三笔申请的在途 ¥50 和已退 ¥50，最终拒绝后在途降至零。
- 已有四进程证据（第 22 讲）：目录涨至 ¥60，旧单仍保留 ¥50。付款交接之前列表无该订单，之后显示实付 ¥150。订单提交发货后两笔库存仍为 `RESERVED`，消费后为 `CONFIRMED`。批查超时订单保留，恢复后刷新成功。以上只覆盖基线，对三种方案使用相同场景进行桌面评审。
- 共部署最小试点：先在隔离环境约束模块接口和仓储访问，保留各自数据归属与事务。再复验收款未交接、退款冲突或重放、发货未出库、批查不可用等结果及恢复责任。若把部分调用改为进程内，需要用模块失败或重启复验等价业务结果，无须复刻 HTTP 故障形态。检查订单写入与 AT、事件消费回执及发件箱在失败下仍按原规则推进。
- 候选切换与退出：先保存原进程的可运行入口与契约。切换时按业务入口和消费职责确认单一活动写入者，原进程中继与消费者交接时保留事件身份、回执和未完成记录。出现跨模块直读写业务表、资金与订单状态被合并、同一额度双写、在途记录无法追踪或关键回归失败，即停止。若已切换，先停止候选接新写入及消费，核对待处理记录，再恢复原入口与消费者。已发生的资金及业务事实继续按原身份核查。
- 独立售后退出条件：按行退款两道上限由订单继续守护。若试点时必须复制可写额度，或无法从工单追溯原订单、订单行和申请，则停止受理新增工单，按原身份保留并处理在途记录，再将新申请交回原入口。
