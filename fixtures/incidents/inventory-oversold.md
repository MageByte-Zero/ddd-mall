# 失败样例：库存账实不符（守恒被破坏 + 并发超卖窗口）

> 脱敏教学夹具；2026-09-29 在 ddd-mall 本机环境真实复现（MySQL 8.0.39、Spring Boot 3.3.5、MyBatis-Plus 3.5.9、Seata 2.2.0）。
> 首次使用：第 12 讲《库存预占与释放：避免超卖的领域设计》。

## 背景

库存类事故有两种形态，常被混为一谈，其实成因相反：

- **超卖**：卖出去的比在库的多，`可售库存` 被扣成负数，用户付了钱拿不到货。
- **账实不符**：库存数量没有变负，但"在库总数"和"可售 + 已占"对不上——
  有一批货既不在可售里，也没有任何字段记录它在哪。

第二种更隐蔽：它不会立刻报错，而是让库存悄悄"少卖"或"虚增"，
直到某次大促对账才被发现。第 10、11 讲的 ddd-mall 就一直处在第二种状态里。

## 复现步骤一：守恒被破坏（真实数据库状态）

第 10、11 讲的库存表只有两个字段，`deduct` 只减 `available_stock`、从不减 `total_stock`。

```sql
-- 第 11 讲实验跑完之后，本机 mall_inventory 库的真实取值
SELECT total_stock, available_stock FROM t_inventory WHERE sku_code = 'SKU-1001';
-- total_stock = 100, available_stock = 93
```

需求文档第 4 节第 2 条写的不变量是「已预占库存 + 可售库存 == 总库存」。代入：

```
0（当时根本没有"已预占"这个字段） + 93  ≠  100
```

**那 7 件去哪了？** 没有任何字段能回答。它可能被订单预占了（但订单表里查不到对应关系），
也可能是被某个失败的事务改坏了——两种都可能，而数据本身不告诉你。

第 12 讲加上 `reserved_stock` 之后，同一个状态变成：

```
93（可售） + 7（已预占） == 100（总库存）   ✅ 守恒成立
```

并且 `Inventory.reconstitute()` 会在重组聚合时当场校验守恒，任何"说不通"的行
在被业务代码用到之前就抛 `InventoryDomainException`，不会带着错误继续参与计算。

## 复现步骤二：并发超卖窗口（受控测量）

超卖的经典成因不是"忘了加锁"，而是**检查与写入之间存在窗口**：

1. 线程 A 读到 `available_stock = 1`，判断"够"；
2. 线程 B 也读到 `available_stock = 1`，也判断"够"；
3. A 写入 `available_stock = 0` 并提交；
4. B 写入 `available_stock = 0`——如果 B 的写是"基于自己读到的值算出来的新值"
   （`SET available_stock = 0`），那 A 的写入被覆盖，库存多卖了一件；
   如果 B 的写是"相对扣减"（`SET available_stock = available_stock - 1`）且没有
   `WHERE available_stock >= 1`，库存会被扣成 -1。

第 12 讲用两层闸门拦这个窗口，实测数据（`InventoryConcurrencyTest`，并发度 64）：

| 实验 | 库存 | 请求数 | 成功 | 被拒 | 终态（总/可售/已预占） |
|---|---|---|---|---|---|
| 防超卖 | 50 | 1000 各抢 1 件 | **50** | 950 | 50 / 0 / 50 |
| 写策略对比·原子条件更新 | 1000 | 1000 各抢 1 件 | **1000** | 0 | 1000 / 0 / 1000 |
| 写策略对比·乐观锁整体保存 | 1000 | 1000 各抢 1 件 | **17** | 983（版本冲突） | 1000 / 983 / 17 |

第一行的 950 次拒绝里，绝大部分是"领域层用读到的快照判断为够、
但 SQL 的 `WHERE available_stock >= n` 已经命中不到"的请求——
也就是**被第二道闸门拦下的超卖**。守恒在三种情况下都成立，可售库存从未变成负数。

## 处理手册（本夹具的实际操作）

1. **发现**：守恒自检在 `Inventory` 的每个动作之后跑一次；
   重组时再校验一次。任何破坏守恒的操作当场抛异常，不会写库。

2. **存量数据校准**：Flyway `V2__inventory_reservation_model.sql` 在加列之后
   把历史"已被扣掉的部分"解释为仍被预占：

   ```sql
   UPDATE t_inventory SET reserved_stock = total_stock - available_stock
   WHERE total_stock > available_stock;
   ```

   **真实项目里这一步必须业务方参与**：这 7 件到底是被订单占着、还是被改坏了，
   数据本身说不清，要拿预占单据去对。教学库直接迁移。

3. **对账**：`t_inventory_log` 记每次变动的前后快照，可以回答
   "这批货是哪一步挪走的"：

   ```sql
   SELECT id, change_type, quantity, available_before, available_after,
          reserved_before, reserved_after, created_at
   FROM t_inventory_log WHERE sku_code = 'SKU-1001' ORDER BY id DESC LIMIT 20;
   ```

4. **告警**：`InventoryConcurrencyException`（409）的出现频率要接监控。
   本讲实测并发释放 100 次只成功 2 次——如果超时批量回收真的这么跑，
   409 会先于超卖出现，是很好的早期信号。

## 教训（写进第 12 讲正文）

- **"库存没变负"不等于"库存是对的"。** 两字段模型下超卖确实被拦住了，
  但守恒一直是破的，代价是查不出账、也无法做超时回收。
- **防超卖需要两道闸门**：领域层用读到的快照判断"够不够"（给出可读的业务错误），
  持久层用 `WHERE available_stock >= n` 判断"写入那一刻还够不够"（拦并发窗口）。
  只留第一道会超卖，只留第二道就只能给用户一个"扣减失败"。
- **乐观锁在热点行上会把并发度兑换成失败率。** 1000 并发下只成功 17 次，
  看起来"耗时更短"是因为 983 个请求什么都没做就被打发了。
  按每个成功请求摊，原子条件更新反而快 6.7 倍。
- **账实不符比超卖更难查**，所以守恒要写进领域层并在重组时校验，
  而不是留给对账脚本事后发现。
